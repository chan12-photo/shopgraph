### 0.1 이 문서의 표기 규칙

| 표기 | 뜻 |
|---|---|

| **[확정-찬일]** | 찬일이 정했지만 아직 팀 합의 전인 사항. 10/24 회의에서 [확정-팀]으로 바꾸거나 수정 |

- 규칙을 바꿀 때는 정의 위치를 고치고, 참조하는 장의 설명이 어긋나지 않는지 같이 확인한다

### 0.2 에이전트가 지켜야 할 원칙

1. **이 문서와 원자료(2장, 3장)를 기준으로 판단한다.** 다른 AI의 피드백, 딥리서치 결과, 인터넷 일반론은 그대로 믿지 말고 이 문서의 확정 사항·교수님 발언과 하나씩 대조해 수용/반려를 판단한다.
2. **범위를 늘리지 않는다.** 교수님이 "너무 많은 기능을 넣지 말고 추천 하나에 집중"하라고 했다(3장). 새 기능 제안은 16장(폐기 목록)과 충돌하지 않는지 먼저 확인하고, 필요하면 "보류 후보"로만 제안한다.
3. **필수 완성 게이트(13주차)를 지킨다.** 필수 기능이 끝나기 전에는 추가·보류 기능 작업을 권하지 않는다.
4. **코드는 에이전트가 작성하되, 11.3장 워크플로우를 한 단계씩 따른다.** 단계마다 계획 → 테스트 먼저 → 구현 → 실행 → 자가 점검 → 검토(상 단계는 독립 검토) → 사람 확인 → 기록 순서를 지키고, 단계 통과 기준(11.3.3)을 만족한 뒤에만 다음 단계로 넘어간다. 멈춤 조건(11.3.4)에 걸리면 계속 고쳐보려 하지 말고 멈춰서 보고한다.
5. **부록 A(AI 지시문)와 부록 B(데이터 계약)를 어기지 않는다.** 표준 라이브러리 외 import 금지, eval/exec/global 금지, 계약에 없는 함수 이름·반환 형식 금지, 지시받은 범위 밖 수정 금지.
6. **테스트를 코드에 맞추지 않는다.** 테스트 기대값은 6장과 부록 B(W12 시연 테스트만 승인된 docs/demo_expected.md)에서만 가져온다. 테스트를 지우거나 skip·expectedFailure 처리하거나 기대값을 코드 결과에 맞게 바꿔서 통과시키는 것은 금지한다. 규칙 자체가 바뀌어 기대값을 고쳐야 할 때는 11.3.8 명세 변경 절차로만 고친다.
7. **실행하지 않은 결과를 보고하지 않는다.** 코드를 실행할 수 없는 환경이면 사용자에게 실행 명령을 주고, 사용자가 붙여준 출력으로만 판단한다.
8. **사실과 추천을 구분해서 말한다.** 확인되지 않은 것은 확인되지 않았다고 말한다. 특히 "규칙대로 계산된다"와 "추천이 좋다", "검사를 통과했다"와 "정확하다"를 섞지 않는다.
9. **코드 작업 중에는 코드·테스트 파일을 만들고 고쳐도 된다.** 0.3의 "파일은 요청할 때만"은 일반 대화 답변에 대한 규칙이다.

### 0.3 사용자 작업 방식 (사용자 선호)

- 사용자 이름: 찬일. 한국어, 반말로 대화한다.
- 검토 요청 시 실제 평가자 시선으로 한 문장·한 단어 단위로 까다롭고 냉정하게 본다. "검사기를 통과했으니 괜찮다"는 식의 근거는 쓰지 않는다.
- 수정할 때 전체를 갈아엎지 말고 문제 있는 부분 중심으로 고친다. 사용자가 "갈아엎자"고 할 때만 전면 재작성한다.
- 한 번에 제대로 한다.
- 파일은 사용자가 명시적으로 요청할 때만 만들고, 평소에는 채팅에 텍스트로 답한다.
- 단계를 차근차근 나눠서 진행하는 것을 선호한다.

## 5. 설계

### 5.1 데이터 (원본)

**고객** (지역, 가입일은 [폐기])

| 속성 | 형식 | 예시 | 쓰이는 곳 |
|---|---|---|---|
| 고객 ID | C01~ (자동 발급, 수정 불가, 재사용 안 함) | C01 | 모든 조회 |
| 이름 | 문자열 | 김하늘 | 화면 표시, 이름 조회 |
| 성별 | 남 / 여 | 여 | 그룹 결정 |
| 나이 | 정수 10~99 | 25 | 연령대 자동 계산 → 그룹 결정 |

**상품** (한 상품 = 한 모델, 색상은 옵션)

| 속성 | 형식 | 예시 | 쓰이는 곳 |
|---|---|---|---|
| 상품 ID | P01~ | P01 | 모든 조회 |
| 상품명 | 문자열 | 오버핏 반팔 티셔츠 | 화면 표시, 이름 조회 |
| 종류 | 상의 / 하의 / 아우터 | 상의 | 조건 조회 |
| 스타일 | 캐주얼 / 미니멀 / 스트릿 / 포멀 | 캐주얼 | 조건 조회 |
| 가격 | 정수(원) | 29000 | 조건 조회 |
| 색상별 재고 | 딕셔너리 {색상: 수량} | {블랙: 5, 화이트: 3, 그레이: 0} | 구매 색상 검증, 품절 판단 |

**구매 기록**

| 속성 | 형식 | 예시 |
|---|---|---|
| 구매 ID | T001~ | T001 |
| 고객 ID | C.. | C01 |
| 상품 ID | P.. | P01 |
| 색상 | 상품의 색상 목록 중 하나 | 블랙 |
| 수량 | 정수 1~99 | 1 |
| 구매일 | YYYY-MM-DD (정확히 10자, 부록 B.3) | 2026-10-01 |

**색상 목록 변경 규칙**: 재고 수정은 색상별 재고 딕셔너리를 **통째로 교체**한다 (새 딕셔너리에 없는 색상 = 삭제). 색상 추가는 언제든 가능. 색상 삭제는 그 색상의 구매 기록이 하나도 없을 때만 가능 (구매 기록이 남아 있는 색상을 지우면 무결성 검사가 깨진다). 재고는 0 이상 정수. 세부는 부록 B.3.

**"상품 = 모델, 색상 = 옵션"을 고른 이유**: 색상마다 상품을 따로 두면(블랙 티 P01, 화이트 티 P02) "같은 옷"이라는 묶음 정보가 따로 필요하다. 모델 하나로 두고 구매 기록에 색상을 적으면, 원본(구매 기록) → 간선 집계 구조에 색상만 더하면 교수님이 말한 가중치가 자연스럽게 나온다.

| 구매 간선 | 고객–상품 쌍마다 1개. 방향 없음, 양쪽에서 조회 |
| 간선 집계값 | 구매한 색상 집합, 구매 기록 수, 총수량, 최근 구매일 (총수량·최근 구매일은 추천에 쓰이지 않고 S1 출력에만 쓰임, 반환 형식은 부록 B.2) |
| 가중치 | 구매한 색상 집합의 크기 (같은 색을 또 사도 가중치는 그대로, 기록 수만 증가) |
| 저장 방식 | 인접 리스트(노드 ID → 이웃 ID 집합). **간선 집계값은 한 곳에만 저장** (예: (고객 ID, 상품 ID) → 집계값). 양쪽에 따로 저장하면 수정 시 값이 어긋나는 버그가 생김 |
| 구매 기록 저장 | 구매 ID를 키로 하는 딕셔너리 (리스트면 ID 조회가 O(R)) |
| 갱신 방식 | 구매 기록이 바뀌는 모든 경우(고객·상품 삭제 포함) 해당 쌍의 집계를 원본에서 다시 계산. 처음에는 전체 재구축(`rebuild()`)으로 시작한다. 재구축은 원본에서 그래프만 다시 만들고 **ID 발급 카운터는 건드리지 않는다** (삭제된 ID 재사용 방지) |
| 고객 0명·구매 0건 노드 | 구매 이력 없는 고객, 아무도 안 산 상품, 소속 고객이 없는 그룹도 노드로 존재 |

**인접 리스트를 고른 이유**: 고객 약 30명 × 상품 약 25개 중 실제 구매 쌍은 일부뿐인 희소 그래프라, 인접 행렬보다 공간과 이웃 탐색 모두 유리하다.

**"클러스터링" 표현 주의**: 머신러닝 군집화가 아니라 규칙(성별·연령대)으로 나눈 그룹이다. 제안서에는 "성별·연령대 그룹"이라고 정확히 쓴다.

**트리·그래프 택일**: 그룹 노드도 하나의 그래프 안에 있으므로 관리 체계는 그래프 하나다. "전체 → 성별 → 연령대 → 고객" 들여쓰기 출력은 출력 형식일 뿐이다.

#### 5.3.2 검색 (그래프 기반, 추천의 부품)

| 번호 | 검색 | 그래프 동작 | 출력 | 추천에서의 역할 | 복잡도 |
|---|---|---|---|---|---|
| S1 | 고객이 산 상품 | 고객 → 상품 | 상품, 구매 색상, 가중치, 구매 기록 수, 총수량, 최근 구매일 | 이미 산 상품 제외 | O(d log d) |
| S2 | 상품을 산 고객 | 상품 → 고객 | 고객, 그룹, 구매 색상 | 근거 출력 | O(d log d) |
| S3 | 그룹 소속 고객 | 그룹 → 고객 | 고객 목록 | 추천의 동료 집합 | O(m log m) |
| S4 | 그룹 인기 상품 | 그룹 → 고객 → 상품 (2단계) | 상품, 점수 = Σ min(가중치, 3), 구매 고객 수, 품절 표시 | 추천 점수 계산과 같은 규칙 | O(m log m + Σ d_c log d_c + q log q) |
| S5 | 함께 구매된 상품 | 상품 → 고객 → 상품 | 상품, 공통 구매자 수 | 없음 | [보류] |

- 기호: d = 그 노드의 차수(이웃 수), m = 동료 고객 수 (S3·S4는 그 그룹 소속 고객 수, 추천은 그 범위에서 모은 동료 수), d_c = 동료 고객 c의 차수, q = 점수가 생긴 상품 수. 색상 옵션 수는 작은 상수로 본다
- 위 복잡도는 "조회할 때마다 정렬한다"는 현재 구현 전제 기준이다. 구현이 바뀌면(예: 정렬된 리스트를 유지) 제안서·보고서의 복잡도도 함께 고친다
- 공통 규칙: 이웃은 항상 ID 순으로 방문하고, 동점은 ID 순 (결과가 매번 같게)
- 복잡도에 정렬이 들어가는 이유: 인접 리스트를 집합(set)에 저장하고, 결정적인 순서를 위해 조회할 때마다 ID 순으로 정렬하기 때문이다. 데이터가 작아 속도 문제는 없지만 제안서에는 정렬 비용을 빼지 않고 쓴다
- **그래프 활용 원칙**: 검색과 추천은 구매 기록 전체를 훑지 않고 반드시 인접 관계(그룹 → 소속 고객 → 이웃 상품)를 따라간다. 결과 테스트만으로는 이 원칙을 확인할 수 없으므로 G6 검토 항목과 G7 질문으로 확인한다 (11.3.3)

#### 5.3.3 핵심 기능: 추천 [방향: 교수님 제안 / 세부 규칙: 추천안] — 추천 규칙의 정의 위치

**정확한 이름: 성별·연령대 그룹의 구매를 집계한 가중 인기 상품 추천.** 추천 함수 하나가 신규 고객과 기존 고객을 모두 처리한다.

```text
recommend(g, 대상 고객 cid, K=3):
  입력 검증: cid 존재, K는 정수 1~10 (bool 제외) → 실패 시 ValueError
  이미 산 상품 = neighbors(cid) 중 상품 노드
  범위 목록 (그래프의 그룹 노드를 따라 동료를 모은다):
      ("group",  [group_of(cid)])                   같은 성별·연령대 그룹 1개
      ("gender", 대상과 같은 성별의 그룹 노드 4개)
      ("all",    그룹 노드 8개 전부)
  선택 = []
  for (범위 이름, 그룹 노드들) in 범위 목록:
      동료 = 그 그룹 노드들의 members() 합집합 − {cid}, ID 순
      for c in 동료:                                   그룹 → 고객
          for p in neighbors(c) 중 상품 노드:           고객 → 상품
              점수(p)   += min(weight(c, p), 3)
              지지자(p) 에 c 추가
      후보 = 점수가 있는 상품 중
             이미 산 상품이 아니고, 모든 색상이 품절이 아니고, 이미 선택에 들어간 상품이 아닌 것
      정렬 = 점수 내림차순 → 구매자 수(= 지지자 수) 내림차순 → 상품 ID 오름차순
      앞에서부터 선택에 추가 (선택이 K개가 될 때까지), 각 항목에 범위 이름 기록
      if 선택이 K개면 중단
  return 선택 (K개보다 적으면 있는 만큼, 0개면 빈 리스트)
```

- 복잡도: 범위마다 O(m log m + Σ d_c log d_c + q log q), m = 그 범위에서 모은 동료 수, 범위는 최대 3개 (기호는 5.3.2)
- **범위 확장의 정확한 목적**: 추천 가능한 상품이 K개 미만일 때 범위를 넓힌다. 데이터가 충분한지(구매자 수·신뢰도)는 판정하지 않는다. 같은 그룹에 구매자가 1명뿐이어도 그 사람이 서로 다른 상품 3개를 샀으면 K=3을 채우고 넓히지 않는다. 그래서 근거(구매 고객 수·고객 ID)를 항상 출력해 보는 사람이 판단하게 한다.
- 넓은 범위로 넘어가도 **좁은 범위에서 이미 뽑힌 상품이 먼저** 온다 (가까운 그룹 우선).
- **점수는 그 상품이 뽑힌 범위 안에서 계산한 값이다.** 범위가 다른 항목끼리는 점수를 비교하지 않는다 (예: 6.3의 C06 결과에서 [전체]의 P02 점수 3이 [남성 전체]의 P01 점수 1보다 아래에 온다). 화면에 범위를 항상 표시하고 이 점을 안내한다.
- 신규 고객은 "이미 산 상품"이 없을 뿐 같은 함수로 동작한다. 같은 그룹의 신규 고객들은 데이터가 같으면 같은 추천을 받는다.
- 출력 예시 (6.3의 C06 경우, 범위 확장이 일어나는 장면):

```text
[추천] 고객6(C06, 남성·10대)님께 추천 (3개)
 1. 오버핏 티셔츠 (P01) - 점수 1, 구매 고객 1명 [남성 전체]
    근거: C04(남성·20대)가 구매
    구매 가능 색상: 그레이, 네이비, 블랙, 화이트
 2. 카고 팬츠 (P04) - 점수 1, 구매 고객 1명 [남성 전체]
    근거: C04(남성·20대)가 구매
    구매 가능 색상: 블랙, 카키
 3. 와이드 슬랙스 (P02) - 점수 3, 구매 고객 2명 [전체 고객]
    근거: C01, C02가 구매 (C02는 2가지 색상 구매)
    구매 가능 색상: 베이지, 블랙
 ※ 같은 그룹(남성·10대)에 다른 고객이 없어 '남성 전체'로, 그래도 3개가 안 돼 '전체 고객'으로 넓혀 찾음
 ※ 점수는 각 범위 안에서 계산한 값이라 범위가 다른 항목끼리 비교하지 않습니다
```

- 색상 가중치의 성격: "다른 색을 또 사면 그 옷을 좋아한다"(교수님 일화)를 **선호 신호로 간주하는 단순 규칙**이다. 일반적인 구매 행동으로 검증된 것은 아니다 (선물·공동 구매일 수 있고, 색상 옵션이 많은 상품이 높은 가중치를 받을 기회도 더 많다).
- 가중치 상한 3의 성격: 고객 1명이 한 상품에 주는 **점수 기여를 최대 3으로 제한**한다. 영향력을 줄일 뿐 독점을 막지는 않는다 (1명이 3색 = 3점 > 2명이 1색씩 = 2점). 같은 점수일 때는 구매자 수가 많은 쪽이 앞선다 (6.2의 P02 vs P01). 3은 검증된 최적값이 아니라 팀이 정한 상수다.
- K 기본값 3, 허용 범위 정수 1~10. 결과가 0개면 view.py가 "추천할 상품이 없습니다"를 출력한다.
- 알려진 한계 (제안서·발표에서 숨기지 말고 밝힐 것)
    - 개인 취향을 추정하지 않는다. 구매 이력이 없는 고객에게 그룹 기반 추천 목록을 **제공**할 뿐, 그 고객에게 맞는 상품을 알아낸 것은 아니다
    - 추천 품질(실제로 살 만한 상품인지)은 검증하지 않았다. 손계산 일치는 "정한 규칙대로 계산된다"는 뜻이다
    - 아무도 사지 않은 신상품은 점수가 없어 추천되지 않는다 (상품 쪽 콜드 스타트)
    - 그룹 인기 집계라서 인기 상품 쏠림(인기 편향)이 남는다
    - '전체'로 넓힐 때 상품의 착용 대상(남/여)을 고려하지 않는다 (모든 상품을 공용으로 가정, 4장)
    - 이미 산 상품은 제외하므로 "같은 옷의 다른 색" 제안은 하지 않는다. 교수님 일화와 가장 가까운 기능이라 보류 1순위 후보로 둔다 (5.3.4)
    - 그룹은 성별·연령대 규칙으로 나눈 것이라 같은 그룹 안의 취향 차이는 반영하지 못한다

| 기존 고객 개인화 (예: 본인이 가중치를 많이 준 스타일 가점) | [보류] | 상품 유사도 측정이 아니라 범주 일치만. 필수 완성 후 |
| 사이즈 추천 (키·몸무게 구간 + 상품 사이즈 옵션) | [보류] | 13주차 필수 완성 후에만, 변경 이력에 사유 기록 |

#### 5.3.5 무결성 검사 check_integrity()

**호출 시점**: 구현은 W5. **W5 이후의 모든 변경 테스트**에서 변경 뒤에 호출해 `[]`인지 확인한다. W3·W4에서 만든 변경 테스트에는 W5에서 이 확인을 **추가**한다 (확인 추가는 허용, 기존 기대값 변경은 금지). 메뉴 [5]에서도 실행 가능.

검사 항목
- 모든 구매 간선이 고객 쪽·상품 쪽 인접 리스트에 둘 다 있다
- 간선 집계(색상 집합, 기록 수, 총수량, 최근 구매일)가 해당 쌍의 구매 기록과 일치한다
- 모든 구매 기록의 고객 ID·상품 ID가 존재하고, 색상이 상품 색상 목록에 있다
- 구매 기록이 없는 쌍에 간선이 남아 있지 않다
- 모든 고객이 정확히 하나의 그룹에 소속되고, 그 그룹이 성별·나이와 맞다
- 노드 수 = 그룹 수 + 고객 수 + 상품 수
- (갱신 방식 검증용) 현재 그래프 = 원본에서 **임시로** 새로 구축한 그래프

**검사는 상태를 바꾸지 않는다 (진단과 복구의 분리)**: `check_integrity()`는 원본·그래프·ID 카운터를 하나도 바꾸지 않는다. 재구축 비교는 원본에서 별도의 임시 그래프를 만들어 현재 그래프와 비교하는 방식으로 하고, 검사 중에 `rebuild()`를 부르지 않는다. 검사하면서 고쳐 버리면 원래의 오류 상태가 사라져 다음 검사와 디버깅이 불가능해진다. 복구 기능은 만들지 않는다.

**검사기 자체의 테스트 (고장 주입)**: 정상 데이터에서 `[]`를 내는 것만으로는 검사기가 일하는지 알 수 없다. 테스트에서 일부러 내부를 망가뜨린 뒤 위반을 보고하는지 확인한다 (6.4). 이 경우에만 테스트가 내부 속성(`_adj`, `_edges`)을 직접 고칠 수 있다.
1. 역방향 간선 하나 제거 (상품 쪽에서 고객 삭제)
2. 집계 조작 (색상 집합에서 색상 하나 제거)
3. 고객을 틀린 그룹에 연결
4. 구매 기록 없는 간선 추가

네 경우 모두 ① 위반을 1건 이상 보고하고 ② **한 번 더 불러도 여전히 위반을 보고하며** ③ 검사 전후 **상태 전체(원본 셋, 그룹, 인접 리스트, 간선 집계, ID 카운터)**가 같아야 한다 (`tests/helpers.py`의 `snapshot`으로 비교. 인접 리스트·간선만 비교하면 검사 중 ID 카운터만 바꾸는 오류를 놓친다) (②③이 "검사가 몰래 고치지 않는다"를 확인한다).

이것은 검사기를 검증하려고 **테스트 안에서** 넣는 고장이다. 사람의 이해를 확인하는 "고장 찾기"(11.3.3, 선택)와는 다르고, 결함 기록에서도 실제 결함과 섞지 않는다 (11.3.9).

**이 검사가 보장하지 않는 것** (제안서·발표에서 과장하지 말 것)
- 갱신과 재구축이 같은 집계 함수를 쓰면 그 함수의 버그는 양쪽에 똑같이 들어가 "일치"로 나온다. 재구축 비교는 **갱신 경로의 일관성**만 확인한다. 집계가 맞는지는 6장 손계산 기대값으로 확인한다
- 원본·그래프가 완벽히 일치해도 추천 정렬·범위 우선순위는 틀릴 수 있다. 추천이 맞는지는 6.3 기대값으로 확인한다
- 정확한 표현: "원본과 파생 그래프의 일관성(정한 불변 조건)을 검사했다". "정확성을 증명했다"고 쓰지 않는다

**함수 목록 초안** [추천안, 회의에서 확정] (제안서 2.2 클래스 다이어그램 겸용, 반환 형식은 부록 B.2)

**고정 단계**: graph.py 계약은 W1에서 고정한다. search.py·view.py의 반환 형식은 W1에서 **가고정**하고, W8b에서 "고객 등록 → 추천 → 출력" 흐름을 실제로 연결해 빈칸을 확인한 뒤 최종 고정한다 (11.3.2).

상태를 어디에 둘지는 두 방법 모두 전역 상태 없이 만들 수 있다: (1) 상태 딕셔너리를 함수 인자로 넘기는 모듈 함수, (2) 클래스. **`ShopGraph` 클래스를 고른 이유**는 원본·그래프·ID 발급 카운터를 한 객체에 묶어 "데이터 변경은 이 객체의 메서드로만"이라는 규칙을 코드 구조로 드러내기 쉽고, 제안서에서 클래스 다이어그램(슬라이드 6쪽의 예시 형식)으로 구조를 설명하기 좋기 때문이다. 슬라이드의 클래스 다이어그램은 예시이지 클래스 사용을 요구한 것은 아니다. 다른 모듈은 이 객체를 인자로 받는다.

Python은 접근을 강제하지 못하므로 규칙으로 정한다 (상태 보호 원칙, 세부는 부록 B.1):
- **내부 속성은 이름 앞에 `_`를 붙인다. 운영 모듈(main·view·search·tools)은 공개 메서드만 쓴다. 테스트는 상태 확인을 위한 읽기·깊은 복사(`tests/helpers.py`의 `snapshot`)를 할 수 있고, 내부 상태를 직접 고치는 것은 고장 주입 테스트에만 허용한다** (새 공개 메서드는 만들지 않음)
- **나가는 쪽: 조회 메서드는 복사본을 돌려준다** (돌려받은 딕셔너리를 고쳐도 내부가 바뀌지 않음)
- **들어오는 쪽: 생성자와 등록·수정 메서드는 외부에서 받은 가변 객체(딕셔너리 등)를 내부 상태와 공유하지 않는다** (생성자의 초기 데이터, `add_product`·`update_product`의 `stock` 모두 복사해서 보관. 호출자가 원래 딕셔너리를 나중에 고쳐도 내부가 바뀌지 않음)

graph.py — `class ShopGraph`
- `__init__(customers=None, products=None, purchases=None)` 초기 데이터를 **검증한 뒤 복사해서** 보관 (생성자 계약은 부록 B.1: 각 인자는 레코드 딕셔너리의 리스트 또는 None, 초기 레코드 ID 형식·중복 검사, 구매가 참조하는 고객·상품 존재 검사, 검증이 끝난 뒤 구성), 8개 그룹 노드 생성, 그래프 구축, ID 발급 카운터 설정
- `add_customer(name, gender, age) -> customer_id`
- `update_customer(customer_id, name=None, gender=None, age=None) -> None`
- `delete_customer(customer_id) -> int` (함께 삭제된 구매 기록 수)
- `add_product(name, kind, style, price, stock) -> product_id` (stock은 복사해서 보관)
- `update_product(product_id, name=None, kind=None, style=None, price=None, stock=None) -> None` (stock은 통째로 교체, 복사해서 보관)
- `delete_product(product_id) -> int`
- `add_purchase(customer_id, product_id, color, qty, date) -> purchase_id`
- `update_purchase(purchase_id, color=None, qty=None) -> None`
- `delete_purchase(purchase_id) -> None`
- `get_customer(customer_id)`, `get_product(product_id)`, `get_purchase(purchase_id)` (복사본, 없으면 ValueError)
- `customer_ids()`, `product_ids()` (ID 순 리스트)
- `find_customers_by_name(name)`, `find_products_by_name(name)` (공백 제거 후 완전 일치, ID 순 리스트)
- `neighbors(node_id) -> ID 순 리스트` (없는 노드면 ValueError)
- `edge(customer_id, product_id) -> 집계값 복사본 또는 None` (없는 고객·상품 ID면 ValueError, 둘 다 있는데 간선이 없으면 None)
- `weight(customer_id, product_id) -> int` (없는 ID면 ValueError, 둘 다 있는데 간선이 없으면 0)
- `group_of(customer_id) -> group_id`, `members(group_id) -> 고객 ID 리스트`
- `is_sold_out(product_id) -> bool`, `available_colors(product_id) -> 정렬 리스트`
- `rebuild()` (ID 발급 카운터는 바꾸지 않음), `check_integrity() -> 위반 목록` (상태를 바꾸지 않음, 5.3.5), `stats() -> 개수 딕셔너리`
- (보류) `save(path)`, `load(path)`

search.py — 읽기 전용 함수, 첫 인자는 `g: ShopGraph`
- `find_products(g, kind=None, style=None, color=None, price_min=None, price_max=None)` (조회)
- `products_of(g, customer_id)` S1
- `customers_of(g, product_id)` S2
- `members_of(g, group_id)` S3
- `group_popular(g, group_id, k=None)` S4 (k=None이면 전체, 아니면 정수 1~10)
- `recommend(g, customer_id, k=3)` 추천
- (보류) `co_purchased(g, product_id)` S5

view.py — 출력 전용
- `print_table(headers, rows)` (한글 폭 계산: unicodedata.east_asian_width)
- `print_group_tree(g)`, `print_recommendation(g, customer_id, result)`, `print_neighbors(g, node_id)`

main.py — 유일한 진입점
- `run()` data.py로 ShopGraph를 만들고 메뉴 루프 실행. data.py는 W8b에서 6장 PoC 데이터로 먼저 채우고, W11에서 시연 데이터로 교체한다 (11.3.2). 입력 문자열 변환(성별 1/2 → 남/여 등)은 main.py가 맡고, ValueError는 메시지로 보여준 뒤 메뉴로 돌아간다

### 5.6 설계 판단 기록 (제안서 2.3에 사용, "다른 안과 비교")

| 결정 | 고려한 다른 안 | 고른 이유 |
|---|---|---|
| 그래프(인접 리스트) | 인접 행렬 | 희소 그래프라 공간·탐색 유리 |
| 고객-상품 쌍마다 간선 1개 + 집계값 | 구매 기록마다 간선 1개(다중 간선) | 검색은 "샀는지·얼마나 좋아하는지"가 중요. 기록은 원본에 따로 보관 |
| 상품 = 모델, 색상 = 옵션 | 색상별 상품 | 가중치(색상 수)가 집계에서 바로 나옴, 노드 수 적음 |
| 가중치 = 색상 수 | 구매 횟수 | 같은 색 반복 구매(소모·교체)보다 다른 색 추가 구매를 선호 신호로 간주 (교수님 일화에서 착안한 가정, 검증된 사실 아님) |
| 가중치 상한 3 | 상한 없음 | 고객 1명의 점수 기여를 제한 (독점을 막지는 않음, 3은 팀이 정한 상수) |
| 성별·연령대 그룹 노드 | 고객끼리 유사도 간선 / 머신러닝 군집 | 교수님 "연령·성별로만 해도 된다", 유사도 측정은 복잡해서 제외 |
| 범위 확장(그룹 → 성별 → 전체) | 빈 결과 출력 | 빈 그룹·후보 부족에서도 K개에 가깝게 채움. 후보 수만 보고 데이터 신뢰도는 판정하지 않음 |
| 간선 집계값 한 곳 저장 | 양쪽 인접 리스트에 각각 저장 | 수정 시 값 불일치 버그 원천 차단 |
| 변경은 graph.py로만, 진입점 main.py 하나 | 각 모듈에서 직접 수정 | 교수님 지적(진입점 여러 개의 위험), 원본·그래프 불일치 방지 |
| 키·몸무게 제외 | 체형 그룹 추가 | 추천 결과에 영향 없음, 그룹 데이터 부족, 입력 증가 |
| 재고 비연동 + 품절 제외 | 구매 시 재고 차감 | 구매 기록은 과거 이력. 연동하면 삭제 시 재고 복원 등 규칙이 연쇄로 생김 |

### 6.3 추천 기대 결과

**비교 기준**: 추천 테스트는 상품 ID 순서만 비교하지 않는다. 항목마다 **상품 ID·범위(scope)·점수·구매자 수·지지자(supporters)**를 모두 비교한다. ID 순서만 보면 범위 확장을 잘못 구현해도 통과할 수 있다 (아래 6번이 그 예).

1. **신규 고객 등록: C07(여, 22)** → G-F-20 자동 연결 → 추천(K=3)

## 7. 시연 시나리오 (D가 데이터를 이 장면에 맞춰 설계)
**발표의 중심**: "추천 시스템을 만들었다"보다 **구매 기록이 바뀔 때 그래프(간선 집계·소속)와 검색·추천 결과가 어떻게 따라 바뀌는지**를 팀원이 설명하고 보여 주는 것이다. 아래 장면 중 3·4·5·6(색상 재구매, 이미 산 상품 제외, 다색 구매로 순위 변화, 품절 제외)과 6장의 마지막 구매 삭제·그룹 이동 사례가 그 설명에 쓰인다.

**기대값**: 장면마다의 기대 결과는 W11에서 시연 데이터를 만든 뒤 D가 손계산하고 C가 검산해 `docs/demo_expected.md`에 적고, 11.3.8 절차로 승인한다. W12 시연 테스트는 이 파일에서만 기대값을 가져온다 (실행 결과를 기대값으로 옮겨 적지 않는다).


1. 그룹별 고객 트리 출력 → 데이터 구조 소개
2. **"25세 여성" 신규 고객 등록 → 자동으로 여성·20대 그룹 연결 → 즉시 추천 + 근거** (교수님이 말한 장면)
3. 그 고객이 추천 1위 상품을 두 가지 색상으로 구매 → S1에서 가중치 2 확인
4. 다시 추천 → 이미 산 상품이 빠지고 다음 순위가 올라옴
5. 다른 여성·20대 고객이 특정 상품을 세 가지 색상으로 구매 → S4 그룹 인기 순위 변화

8. 무결성 검사 → 정상 (발표 표현: "원본과 그래프가 일치함을 확인", "정확성 증명"이라고 하지 않음)

**시연용 더미 데이터 설계 원칙 (D)**
- 고객 약 30명, 상품 약 20~25개(상품당 색상 2~4개), 구매 약 100~150건
- 그룹별 선호 패턴: 예) 여성·20대 → 미니멀 하의, 남성·20대 → 스트릿, 30대 → 포멀·미니멀

- 소속은 있지만 구매가 적은 그룹, 소속 고객이 없는 그룹 1개 이상
- 일부 색상 품절, 전부 품절 상품 1개
- 동명이인 1쌍
- 구매일은 모두 `YYYY-MM-DD` 형식, 9~10월에 고르게 분포
- 상품은 남녀 공용으로 볼 수 있는 의류 위주 (착용 대상 미고려 한계가 시연에서 어색하게 드러나지 않게, 4장)

### 8.2 작성 원칙

- 추천은 과제 양식상 "추가 기능"이지만 이 프로젝트의 핵심으로 쓰고, 팀 일정에서는 필수 범위로 다룬다
- 약속은 3층으로: 반드시(CRUD+P, 검색 S1~S4, 추천, 무결성 검사) / 추가(근거 출력 강화) / 확장 계획(파일 저장, S5, 개인화, 사이즈 추천). 무결성 검사는 W5·W12 완료 기준에 들어가는 내부 검증이라 "반드시"에 둔다
- 추천 표현 수준: "성별·연령대 그룹의 구매를 집계한 가중 인기 상품 추천", "구매 이력이 없는 고객에게도 그룹 기반 추천 목록을 제공", "후보가 K개 미만이면 범위를 넓힘". "콜드 스타트 해결", "개인 맞춤 추천", "쏠림 방지"라고 쓰지 않는다 (5.3.3)
- 복잡도는 5.3.2 기준(정렬 비용 포함)으로 쓴다
- "클러스터링" 대신 "성별·연령대 그룹"
- AI가 쓴 매끈한 문장을 그대로 넣지 않는다. 팀이 내린 설계 결정과 그 이유(5.6)를 직접 쓴다 (교수님: 요즘 제안서는 AI 덕에 다 잘 쓴다)

### 11.2 AI 도구 사용 규칙

교수님은 바이브 코딩을 허용하는 분위기였지만(공식 규정은 아님), 꼬임·확장성·진입점 문제를 경고했다. 10/23 결정에 따라 **코드는 AI가 작성하고, 사람은 설계·기대값·승인을 맡는다.** 아래 규칙은 에이전트에게도 똑같이 적용하며, 실제 진행 절차는 11.3장을 따른다.

AI가 지켜야 할 규칙(금지 행동, 멈춤 조건, 테스트·실행 규칙)은 **11.3과 부록 A에만** 정의한다. 여기에는 사람(담당자)이 지킬 규칙만 둔다.

- 설계(기능 정의 → 데이터 구조 → 함수 목록)는 사람이 먼저 확정하고, AI에는 **한 단계씩** 맡긴다 (11.3.2)
- 부록 A를 저장소 루트의 CLAUDE.md로 두고, 단계를 시킬 때는 11.3.7 요청 형식으로 범위·손대지 말 것을 적는다
- 커밋 전 `git diff`로 바뀐 줄을 직접 읽고, 설명 못 하는 줄이 있으면 합치지 않는다
- 표준 라이브러리가 아닌 import는 무조건 반려, `pip install`은 팀 합의 없이 금지
- AI가 작업하기 전에 먼저 커밋하고, 자기 브랜치·자기 모듈에서만 작업시킨다
- 테스트 기대값은 담당자가 6장·부록 B와 직접 대조한다. `# [제안 기대값]`은 사람이 승인하기 전에는 확정이 아니다
- AI가 "통과했다"고 하면 실행 출력 원문을 확인한다. 에이전트가 실행할 수 없으면 사람이 실행해서 출력을 붙여준다
- 멈춤 보고(11.3.4)를 받으면 담당자가 원인을 판단하고 선택지를 고른 뒤 다시 진행시킨다
- AI가 코드를 쓰더라도 **담당자는 자기 모듈을 설명할 수 있어야 승인할 수 있다** (11.3.3 G7, 11.3.6)
- 발표 전 각자 자기 모듈을 다른 팀원에게 5분 설명

### 11.3 AI 개발 워크플로우 (코드는 AI가, 품질은 게이트가) — 단계·게이트·통과 기준의 정의 위치

바이브 코딩의 문제는 AI가 코드를 쓰는 것이 아니라 **아무도 코드를 보지 않고 확인하지 않는 것**이다 (12장). 이 워크플로우는 AI가 코드를 쓰되, 단계마다 테스트·점검·검토·사람 확인을 거쳐야 다음으로 넘어가게 만든다.

이 절차가 지키려는 것은 형식이 아니라 다섯 가지다: **① 실제 실행 결과 확인 ② 변경 전후 diff 확인 ③ 잘못된 입력의 무변경 보장 ④ 기대값의 사람 확인 ⑤ 담당자의 핵심 로직 설명.** 단계의 위험도에 따라 나머지 절차의 무게를 다르게 둔다 (검토 수준 상/하).

검토 단계가 많다고 서로 다른 오류를 잡는 것은 아니다. 각 장치가 잡는 오류가 다르다: 손계산 기대값 = 규칙 계산 오류 / 무결성 검사 = 원본·그래프 불일치 / 고장 주입 = 검사기가 일하지 않는 문제 / diff 검토 = 범위 밖 변경·중복·죽은 코드 / 이해 질문 = 설명 못 하는 코드. 어느 것도 "추천이 좋은지"는 잡지 못한다.

#### 11.3.1 역할 나누기

| 누가 | 하는 일 |
|---|---|
| 사람 (모듈 승인 담당자, 10장) | 기능 범위, 데이터 계약(부록 B) 승인, 테스트 기대값(6장) 확인, 각 단계 승인, 멈춤 상황 판단 |
| AI (구현 역할) | 단계 계획 초안, 테스트 코드 작성(기대값은 문서에서 옮김), 구현, 실행, 자가 점검, 수정, 기록 |
| AI (검토 역할) | 구현 대화와 **분리된** 새 대화 또는 서브에이전트에서 검토 (G6) |

- **독립 검토**라고 부를 수 있는 것은 구현 대화와 분리된 새 대화·서브에이전트의 검토뿐이다. 같은 대화에서 "처음 보는 검토자" 역할로 바꾸는 것은 **자기 재검토**로 기록하고, 필수 게이트에서는 독립 검토로 인정하지 않는다.
- 원칙: **한 번에 한 단계, 한 단계는 한 모듈의 함수 몇 개 + 그 테스트, 단계 끝 = 커밋 1개.**

#### 11.3.3 한 단계의 사이클 (G1~G8)과 단계 통과 기준

**단계 통과 기준** (G4·G7에서 이 기준으로 판정)
1. 이번 단계의 통과 대상 테스트(11.3.2 표)가 전부 통과
2. 이전 단계 테스트 전부 통과 = 회귀 0
3. 아직 오지 않은 단계의 테스트는 **`NotImplementedError`로만** 실패해야 한다. 다른 오류(AssertionError, KeyError 등)로 실패하면 이번 단계가 무언가를 깨뜨렸을 수 있으므로 원인을 조사한다
4. W8부터는 test_graph·test_search·test_recommend 전부 통과, W12부터는 전체 통과
5. 미도래 테스트를 skip·expectedFailure로 처리하지 않는다. 그대로 두고 분류만 한다

**G1 계획 (AI)**: 이번 단계의 목표, 만들거나 고칠 함수, 수정 허용 파일, **손대지 않을 파일**, 통과 대상 테스트, 예상 위험을 10줄 이내로 제시한다.

**G2 테스트 먼저 (AI)**: 이번 단계 테스트를 먼저 쓰거나(W2에서 이미 쓴 것은 확인만) 부족한 경계 상황 테스트를 추가한다. 기대값은 6장·부록 B(W12는 승인된 docs/demo_expected.md)에서만 옮긴다. 문서에 없는 기대값이 필요하면 `# [제안 기대값]` 주석을 달고 G7에서 사람 승인을 받는다.
- 새 테스트를 구현 전에 실행해 결과를 기록한다. 실패하면 정상이다.
- 처음부터 통과하는 테스트는 버리지 않고, **이미 구현된 어떤 로직이 처리하는지 한 줄로 적는 것**으로 충분하다. 기존 검증 로직이 새 잘못된 입력을 이미 잘 처리하는 것은 자연스러운 일이다.
- **대표 고장 검사는 핵심 규칙에만** 한다: 무결성 검사기(5.3.5 고장 주입), 추천의 범위 확장·상한·정렬(6.3-6번처럼 잘못된 구현과 구별되는 사례), 실패 시 무변경. 이때 확인하는 것은 "테스트가 **겨냥한 동작**을 깨뜨리면 실패하는가"이다. 임의의 코드 한 줄을 바꿨는데 통과했다는 사실만으로는 테스트가 무의미하다고 단정하지 않는다 (그 줄이 그 입력에서 실행되지 않거나, 바꿔도 결과가 같을 수 있다).

**G3 구현 (AI)**: 계약(5.5·부록 B) 그대로, 이번 단계 함수만 최소로 고친다. 이미 승인된 함수를 다시 생성하지 않는다. 검색·추천은 인접 관계를 따라가게 쓴다 (5.3.2 그래프 활용 원칙).

**G4 실행 (AI 또는 사람)**: `python -m unittest -v` 전체를 실행하고, 결과를 **통과 N / 미도래(NotImplementedError) N / 실패·오류 N**으로 분류한다. 실패·오류는 테스트 이름과 메시지 원문을 그대로 보여준다. 실행할 수 없는 환경이면 사람에게 명령을 주고 출력 전문을 받는다.

**G5 자가 점검 (AI)**: 아래 체크리스트를 항목별로 "확인함 / 해당 없음 / 문제 있음"으로 표시한다. 가능한 항목은 검색 명령(grep 등)으로 확인하고 명령과 결과를 같이 적는다.

- [ ] import가 표준 라이브러리뿐이다
- [ ] eval, exec, global, `except: pass`가 없다
- [ ] 데이터 변경이 ShopGraph 메서드 안에서만 일어난다
- [ ] 운영 모듈(search·view·main·tools)이 ShopGraph 내부 속성(`_`로 시작)을 쓰지 않는다. 테스트는 `snapshot`을 통한 읽기만, 직접 수정은 고장 주입 테스트에만 있다
- [ ] 조회 메서드가 복사본을 돌려주고, 생성자·등록·수정 메서드가 받은 가변 객체를 복사해서 보관한다
- [ ] `check_integrity()`가 상태를 바꾸지 않는다 (검사 중 `rebuild()` 호출 없음)
- [ ] 함수 이름·인자·반환 형식이 5.5·부록 B와 일치한다
- [ ] 이번 단계에 해당하는 경계 상황(부록 B.4)마다 테스트가 있다
- [ ] 실패 입력 뒤 `snapshot(g)` 전체(원본 셋·그룹·인접 리스트·간선 집계·ID 카운터)가 그대로다. 유효한 값과 틀린 값을 섞은 수정도 확인했다
- [ ] 테스트 고정 데이터를 `tests/fixtures.py`의 함수로 테스트마다 새로 만든다 (모듈 수준 딕셔너리 공유 없음). 고정 기대값 테스트가 실행용 data.py를 읽지 않는다

- [ ] 같은 일을 하는 함수가 두 개 없다
- [ ] print가 view.py·main.py·tools/에만 있다
- [ ] 결과 순서가 결정적이다 (ID 순, 동점 규칙 5.3.3)
- [ ] docstring이 실제 동작과 일치한다
- [ ] 수정 허용 파일 밖에 변경이 없다
- [ ] 테스트 삭제·skip·expectedFailure·기대값 변경이 없다
- [ ] 특정 ID·입력에만 맞춘 하드코딩이 없다

**G6 검토 (AI)**: 검토 수준 **상** 단계는 독립 검토(새 대화 또는 서브에이전트), **하** 단계는 생략하거나 자기 재검토로 대신할 수 있다. 검토자에게 주는 자료:
- 부록 A·B
- 이번 단계와 관련된 규칙 원문 (예: 추천이면 5.3.3 전체, 검색이면 5.3.2, 무결성이면 5.3.5)
- 이번 단계와 관련된 6장 기대값
- G1 계획, diff, G4 출력
- **diff가 호출하는 기존 함수의 본문** (기존 코드와의 상호작용을 보기 위해)

지적 사항은 "반드시 수정 / 권장 / 무시(사유)"로 분류하고, 반드시 수정이 있으면 G3로 돌아가 고친 뒤 G4부터 다시 한다.

```text
[검토 지시]
너는 이 코드를 처음 보는 검토자다. 아래 계약(부록 A·B), 관련 규칙 원문, 기대값, 이번 단계 계획을 기준으로 diff를 검토해라.
1. 계약과 다른 함수 이름·인자·반환 형식이 있는가 (복사본 반환 규칙 포함)
2. 계획에 없는 파일·함수가 바뀌었는가
3. 경계 상황(부록 B.4) 중 처리하지 않은 것이 있는가
4. 잘못된 입력에서 상태가 일부만 바뀌는 경로가 있는가
5. 데이터 변경이 ShopGraph 밖에서 일어나거나, 다른 모듈이 내부 속성(_)을 쓰는가
6. 바뀐 코드가 호출하는 기존 함수의 전제(인자 형식, 예외, 반환값)와 맞는가
7. 검색·추천이 구매 기록 전체를 훑지 않고 인접 관계를 따라가는가
8. 중복 로직, 죽은 코드, 쓰이지 않는 인자가 있는가
9. 테스트가 실제로 동작을 검사하는가 (항상 통과하는 테스트, 구현을 그대로 베낀 기대값이 있는가)
10. docstring과 실제 동작이 다른 곳이 있는가
각 지적마다 파일·줄·이유·제안을 쓰고 "반드시 수정 / 권장"으로 분류해라. 문제가 없으면 없다고 써라.
```

**G7 사람 게이트 (담당자)**: AI가 아래를 한 번에 제출하고, 담당자가 "승인" 또는 "수정 요청"으로 답한다.

- 변경 요약 (5줄 이내)
- diff 또는 바뀐 함수 목록
- G4 실행 출력과 분류 (통과 / 미도래 / 실패)
- G5 체크리스트 결과
- G6 검토 지적과 처리 결과 (독립 검토인지 자기 재검토인지 표시)
- 남은 위험·한계
- **이해 확인 질문** (검토 수준 상 = 3개, 하 = 1개). 질문 종류를 섞는다:
    - 예측: 새 입력에서 결과를 예측 (예: "C03에게 K=2로 추천하면 무엇이 어떤 범위로 나오나?")
    - 원인: 실패 상황의 원인 찾기 (예: "T004 삭제 후 최근 구매일이 2026-10-01로 남아 있다면 어느 함수를 의심해야 하나?")
    - 설명: 설계 이유 (예: "같은 색을 또 사면 가중치가 왜 그대로인가?")
- 모범 답은 질문과 분리해 접어두고, 담당자가 먼저 스스로 답한 뒤 확인한다. **하나라도 답하지 못하면 승인하지 않고 그 부분 설명을 요청한다.**
- **고장 찾기 (선택, 10/24 회의에서 여부 결정)**: 이해 질문의 한계(읽고 따라 말하기와 새 상황에서 원인 찾기를 구분 못 함)를 보완하는 연습이다. 하기로 하면 W5·W8에서 한 번씩: AI가 한 줄짜리 버그를 넣은 임시 브랜치를 만들고, 담당자가 테스트 출력과 코드만 보고 원인 줄을 찾는다. 끝나면 임시 브랜치는 지운다. 필수 절차가 아니며, 결과는 연습 기록이지 실제 결함 발견 사례가 아니다 (11.3.9 분류 C).

**자동 진행 모드**: 담당자가 "자동 진행"이라고 하면 **일반 단계**는 G7의 승인 대기를 생략하고 G8 후 다음 단계로 넘어간다. 단,
- **이해 확인 질문은 생략하지 않는다.** 질문을 그 단계 커밋 본문의 "미답 질문"에 남기고, 담당자는 다음 단계가 끝나기 전(늦어도 다음 날)까지 답한다
- 미답 질문이 2단계 넘게 쌓이면 자동 진행을 멈춘다
- **필수 게이트 단계(W1, W2, W5, W8, W8b, W12, W13)와 멈춤 조건(11.3.4)에서는 반드시 멈춘다.** 생략한 단계의 G7 자료는 모아 두었다가 다음 필수 게이트에서 한꺼번에 제출한다

**G8 기록 (AI)**: 커밋 메시지 `[AI][W번호] 내용` + 본문(바뀐 함수, 테스트 분류 변화, 검토 지적 처리, 미답 질문, **실제 소요 시간**). 발견한 결함은 docs/defects.md에 기록(11.3.9). 설계·계약이 바뀐 경우 **19장 변경 이력·6.6 검증 기록에 넣을 문안을 G7 자료에 함께 제출하고, 사람이 계획서 본문에 반영한다** (AI는 계획서 본문을 고치지 않는다). 그다음 단계의 G1을 제안한다.

**사람 시간 추정** (추정치. 실제 소요 시간을 G8에 기록해 처음 3단계 뒤 다시 맞춘다)
- 이 숫자는 **승인 담당자 한 명이 단계마다 쓰는 기본 검토 시간**이다. 재검토·수정 요청 왕복, 담당자의 학습 시간, 공동 승인에 참여하는 다른 사람의 시간, 제안서·발표자료 작업은 들어 있지 않다. 팀 전체 작업량으로 읽으면 낙관적이다
- 검토 수준 상 1단계: 약 40~60분 (계획 확인 5, 기대값 대조 10~15, diff 읽기 15~20, 질문·승인 10~15)
- 검토 수준 하 1단계: 약 15~20분
- 상 10개(W1~W5, W7, W8, W8b, W12, W13) + 하 6개(W0, W6, W9, W10, W11, W14) ≈ 기본 검토 시간 합계 약 9~12시간 (고장 찾기를 하면 +1시간). 4명이 나누면 1인 약 3시간 안팎 / 6주 + 위에서 뺀 시간
- **초과 시 줄이는 순서** (실측이 추정의 2배를 넘을 때 위에서부터 하나씩 적용. 모두 실제로 무언가를 줄인다)
    1. 필수 게이트가 아닌 상 단계(W3, W4, W7)를 하로 내린다 → 독립 검토 생략, 이해 질문 3개 → 1개
    2. 독립 검토(G6)는 필수 게이트(W1, W2, W5, W8, W8b, W12, W13)에서만 하고, 나머지는 자기 재검토로 기록한다
    3. 주 1회 5분 모듈 설명을 필수 게이트 직후에만 한다 (6주 동안 약 6회 → 4회)
    4. 고장 찾기(선택)를 하고 있었다면 중단한다
- **줄이지 않는 것**: 11.3 첫머리의 ①~⑤ (실제 실행 결과 확인, diff 확인, 잘못된 입력의 무변경, 기대값의 사람 확인, 담당자의 핵심 로직 설명)

#### 11.3.4 멈춤 조건 (AI는 즉시 멈추고 보고)

- 같은 실패(같은 테스트, 같은 오류 종류)를 **같은 원인 가설로 3회** 고쳐도 실패한다
- 원인과 상관없이 한 단계 안에서 수정 시도가 **총 6회**를 넘는다 (가설을 바꿔 가며 계속 도는 것을 막는 상한)
- 테스트를 통과시키려면 테스트 기대값, 계약(5.5·부록 B), 문서 규칙 중 하나를 바꿔야 한다 (→ 11.3.8 절차 제안)
- 수정 허용 파일(11.3.2 표) 밖의 파일·함수를 고쳐야 한다
- 미도래 테스트가 `NotImplementedError`가 아닌 오류로 실패하는데 원인을 찾지 못했다
- 명세가 모호하거나 문서끼리 서로 다르다
- W12에서 docs/demo_expected.md에 없는 기대값이 필요하다 (→ 실행 결과를 옮겨 적지 말고 D·C에게 손계산 요청)
- 표준 라이브러리 밖 패키지가 필요해 보인다
- data.py를 크게 고치거나 지워야 한다 (W11 제외)
- 실행 결과를 확인할 수 없는데 "통과"라고 말해야 하는 상황이다 (→ 금지, 사람에게 실행 요청)

보고 형식: 무엇을 하다가 / 무엇이 막혔는지(오류 원문) / 시도한 가설과 결과 / 선택지 2~3개와 추천 / 각 선택지가 바꾸는 범위.

#### 11.3.5 금지 행동 (바이브 코딩 실패 패턴)

- 테스트를 지우거나, skip·expectedFailure 처리하거나, 기대값을 코드 결과에 맞게 바꾸기 (11.3.8 명세 변경 절차만 예외)
- 실행하지 않은 테스트를 통과했다고 보고하기
- 특정 ID·입력일 때만 맞는 결과를 내도록 하드코딩하기
- `try/except`로 오류를 삼켜 숨기기 (`except: pass`, 모든 예외를 잡고 무시)
- 요청 범위 밖 리팩토링, 이름 바꾸기, 파일 옮기기
- 이미 승인된 파일을 처음부터 다시 생성하기
- 한 단계에서 여러 모듈을 동시에 크게 바꾸기
- 계약에 없는 공개 함수를 추가하기 (필요하면 멈춤 조건으로 보고)
- 내부 객체를 그대로 반환하거나, 다른 모듈에서 내부 속성(`_`)을 쓰기

#### 11.3.6 이해·설명 보완 (AI가 코드를 쓰기 때문에 반드시 필요)

교수님은 로직과 "코드 설명"을 평가하고(2.1, 2.2), 결과보고서에는 주석으로 코드 설명이 들어간다. Anthropic 연구에서는 AI 도움을 받은 그룹의 이해도 퀴즈 점수가 직접 짠 그룹보다 낮았다 (12장). 이 연구가 "질문 몇 개로 이해도가 유지된다"는 것을 입증하지는 않으므로, 아래는 효과가 증명된 방법이 아니라 **설명 못 하는 코드를 줄이기 위한 최소 장치**다.

- 이해 확인 질문을 건너뛰지 않는다 (자동 진행 모드에서도 미답 질문으로 남긴다)
- (선택) W5·W8에서 고장 찾기를 한다 (11.3.3, 회의에서 결정)
- 주 1회, 담당자가 자기 모듈을 다른 팀원에게 5분 설명한다
- 결과보고서 주석·코드 설명은 AI 초안을 담당자가 읽고 자기 말로 고친다
- (선택, 찬일) 코딩테스트 연습으로 search.py의 그룹 탐색·정렬 로직을 AI 코드를 보지 않고 한 번 손으로 다시 짜보고, 6장 테스트로 확인한다

#### 11.3.7 에이전트에게 단계를 시킬 때 쓰는 요청 예시

```text
계획서 11.3 워크플로우로 W5를 진행해줘.
- 범위: graph.py의 add_purchase, update_purchase, delete_purchase, 날짜 검증, check_integrity
- 수정 허용: graph.py, tests/test_graph.py (테스트는 추가만, 기존 기대값 변경 금지)
- 손대지 말 것: search.py, view.py, main.py, data.py, 다른 테스트 파일
- 통과 기준: test_graph.py 전부 통과, 고장 주입 4종 검출, 미도래 테스트는 NotImplementedError로만 실패
- G6은 서브에이전트로 독립 검토, G7에서 멈춰서 이해 질문 3개
```

#### 11.3.8 명세 변경 절차 (승인된 기대값·계약을 바꿀 때)

AI가 테스트를 코드에 맞추는 것(금지)과, 팀이 규칙을 바꿔 기대값을 다시 계산하는 것(허용)을 구분한다.

1. 변경 제안: 무엇을 왜 바꾸는지, 영향받는 6장 항목·테스트·함수 목록
2. 재계산: 바뀐 규칙으로 6장의 영향받는 값을 다시 계산 (계산 스크립트 + 손계산 1건 이상)
3. 승인: 해당 모듈 담당자 + 다른 팀원 1명
4. 기록: AI가 19장 변경 이력·6.6 검증 기록에 넣을 문안을 제출하고, 사람이 계획서 본문에 반영한다
5. 커밋 분리: 기대값·계약 변경은 `[SPEC][W번호]` 커밋으로 따로 하고, 구현 변경과 한 커밋에 섞지 않는다

10/24 회의에서 4장의 [추천안]이 바뀌는 경우도 이 절차를 따른다.

#### 11.3.9 결함 기록 (발견한 문제를 출처별로 구분해 남긴다)

결함 기록은 이 프로젝트에서 무엇을 어떻게 확인했는지 보여 주는 **근거 중 하나**다. 유일한 근거는 아니다: 설계 대안의 비교(5.6), 요구사항과 테스트의 연결(docs/test_map.md), 실제 동작 시연, 변경 요청에 대응한 판단(19장)도 같은 무게로 설명할 수 있는 내용이다. 또 발견한 결함 수가 많다고 절차가 좋은 것은 아니다. 구현이 허술해서 많을 수도 있고, 설계 단계에서 잘 예방해서 적을 수도 있다. **개수를 목표나 성과 지표로 쓰지 않는다.**

`docs/defects.md`에 한 줄씩 남기되, **출처를 세 갈래로 나눠 절대 합산하지 않는다**.

|---|---|---|
| A. 구현 결함 | 실제 구현 중 G4 테스트 실패, G6 검토, G7 질문, 멈춤 보고, 무결성 검사로 발견한 결함 | (구현 시작 후 채움) |
| B. 계획·명세 문제 | 계획서·계약·기대값 검토에서 발견한 빈칸·충돌·과장 (코드 이전) | 재구축 시 삭제된 ID 재사용 가능성(2차 재검토), 같은 성별 범위 확장을 구별하는 사례 부재(3차 재검토), 검증 중 테스트 고정 데이터 공유로 테스트가 잘못 실패(3차 재검토) |
| C. 의도적 주입 | 검사기 검증(5.3.5 고장 주입)이나 이해 연습(고장 찾기)을 위해 일부러 넣은 고장 | 고장 주입 4종, 고장 찾기 결과 |

|---|---|---|---|---|---|---|---|

- 결함이 없었던 단계도 "발견 0"으로 남긴다 (부풀리지도 숨기지도 않음)
- 결과보고서에는 분류별 요약을 넣는다

## 12. 바이브 코딩 주의 근거 요약

**읽는 법**: 아래 연구는 "AI가 쓴 코드는 검토와 이해 확인이 필요하다"는 **배경**이다. 오른쪽 "대응"은 이 배경에 맞춰 둔 장치일 뿐, 그 장치가 효과적이라는 증거가 아니다. 각 연구의 대상·조건은 이 팀(학생 4명, 신규 콘솔 프로젝트)과 다르므로 수치를 이 프로젝트에 그대로 옮기지 않는다. 이 프로젝트에서 절차에 대해 말할 때는 실제 기록(결함 기록 11.3.9, 요구사항↔테스트 대응표, 단계별 실행 출력)을 근거로 쓰고, 연구 수치를 이 절차의 효과처럼 인용하지 않는다.

| 문제 | 근거 | 이 프로젝트에서의 대응 |
|---|---|---|
| 정의 | Karpathy(2025-02-02)가 "코드의 존재를 잊는" 방식으로 처음 사용. Simon Willison: AI가 짠 코드를 검토·이해했다면 소프트웨어 개발, 아니면 바이브 코딩 | 문제는 AI 사용이 아니라 코드를 안 보는 것 |
| 품질 저하, 수정 중 엉뚱한 곳 파손 | Martin Fowler: 저품질 코드가 빠르게 쌓여 LLM도 수정하기 어려워지고, 비결정성 때문에 안 바뀌어야 할 곳에 오류가 들어감 | 함수 단위 요청, 수정 범위 명시, diff 확인 |

## 17. 찬일 개인 목표 메모 (포트폴리오·코딩테스트)

- 이 프로젝트를 대기업 취업 포트폴리오로도 쓰려고 한다. **냉정한 평가: 결과물은 작은 더미 데이터, 콘솔 화면, 규칙 기반 그룹 추천이라 기술적 차별성이 제한적이다. 메인 포트폴리오로는 약하고 보조 소재로만 쓴다.** AI 작성 사실을 공개하고 승인 기록을 남긴다고 해서 평범한 과제가 강한 포트폴리오로 바뀌지는 않는다
- **10/23 결정으로 코드는 AI가 작성한다. 따라서 포트폴리오·자소서·면접에서 "직접 구현했다"고 쓰면 안 된다.** 쓸 수 있는 표현의 방향: "기능·데이터 구조·검증 기준을 설계하고, AI 코딩 에이전트의 구현을 단계별 테스트와 검토로 확인했다." (dart-review-agent를 "구현에는 AI 코딩 에이전트를 활용, 기능 범위와 평가 기준을 정하고 검수"로 쓴 것과 같은 구조)
- **설명할 가치가 있는 것은 절차의 이름이 아니라 구체적인 판단과 발견이다.** 설명할 수 있는 근거는 여러 가지다: 설계 대안을 비교하고 고른 이유(5.6), 요구사항을 테스트로 연결한 방식(docs/test_map.md), 실제 동작 시연, 규칙 변경에 대응한 판단(19장), 구현 중 실제로 잡은 결함(11.3.9 분류 A). 결함 기록은 그중 하나이고, 분류 C(의도적으로 넣은 고장)는 실제 결함 사례로 말하지 않는다
- 주의: 재구축 시 ID 재사용, 범위별 점수의 의미, 조회 반환값을 통한 원본 변경, `date.fromisoformat` 함정은 **10/23 계획 검토에서 외부 AI 리뷰와 Claude 대조로 찾은 설계 보완**이다. 면접에서 쓴다면 "계획 단계에서 AI 리뷰를 원문·실행 결과와 대조해 수용 여부를 판단했다"는 범위로만 말하고, 내가 혼자 찾은 것처럼 말하지 않는다. 구현 중 실제로 테스트나 검토로 잡힌 결함은 결함 기록에 따로 남는다
- 과장 금지 표현과 바꿔 쓸 표현
    - "콜드 스타트 해결" → "구매 이력이 없는 고객에게 그룹 기반 추천을 제공"
    - "무결성 검사로 정확성 증명" → "정한 데이터 불변 조건과 집계 일관성을 검사"
    - "AI 코드를 믿을 수 있게 만든 검증 체계" → "특정 오류를 탐지하고 회귀를 확인하는 검토 절차를 적용"
    - "쏠림 방지" → "고객별 점수 기여를 최대 3으로 제한"
- 면접에서 AI가 쓴 코드라도 한 줄씩 설명하고, 새 입력에서 결과를 예측하고, 버그 원인을 찾을 수 있어야 한다. 읽고 따라 말하는 수준이면 오히려 감점 요인이 된다 (11.3.6)
- 코딩테스트 준비와의 연결은 약해진다. AI가 탐색 로직을 짜면 탐색 연습 효과가 없으므로, 원하면 11.3.6의 "손으로 다시 짜보기"를 따로 한다
- 권장 역할: **C(검색·추천)**. 이유: 추천 규칙(색상 가중치, 상한, 범위 확장, 범위별 점수 의미)의 설계 판단을 직접 내렸고 그 이유를 설명할 수 있다. "추천이 핵심이라 가장 좋은 역할"이라서가 아니다. B(그래프 엔진)는 변경·일관성을 깊이 다루는 역할이라 데이터 엔지니어 방향이면 B도 같은 가치가 있다 (10장)
- 면접 소재 (정확한 표현으로): 구매 이력이 없는 고객에게 성별·연령대 그룹 노드로 추천 목록을 제공하고 후보가 부족하면 상위 범위로 넓힌 설계 / 색상 재구매를 선호 신호로 간주한 가중치와 기여 상한, 그 가정의 한계 / 원본·집계 분리 / 진입점 하나·변경 통로 하나·복사본 반환 / 원본과 그래프의 일관성 검사와 고장 주입으로 검사기 자체를 확인한 것 / 교수님 일화에서 얻은 "입력 최소화" 설계 원칙 / 결함 기록의 구체 사례
- 포트폴리오 조건: 자기 계정 커밋(`[AI]` 표시 포함), 설계 판단 메모, 결함 기록(11.3.9), 교수님 공개 허용 + 팀원 동의. 팀 결과와 개인 몫을 구분하고, AI가 한 일과 내가 한 일도 구분해서 쓴다 ("팀은 ~했고, 저는 ~을 맡았습니다. 구현에는 AI 코딩 에이전트를 활용했고, 저는 ~을 설계·검증했습니다")
- 기존 실행 계획에 "포트폴리오용 확장(UCI 표본, 추천 평가, SQL 대조)은 이영민 님 개인 작업"으로 적혀 있었다 → 팀 회의에서 범위 합의 필요
- 시점: 프로젝트 완성은 12월 중순이라 2026 하반기 지원서에는 못 쓰고, 2027 상반기 공채부터 사용 가능. 미완성 상태에서 성과를 앞당겨 쓰지 않는다
- 수업 후 개인 확장(선택, 12월 말~1월): 실데이터 적용, 추천 품질 평가(시간 분할 적중률), SQL 대조. 지원 방향(IT·SW·데이터 엔지니어)일 때만 할 가치가 있다

## 부록 B. 데이터 계약과 검증 규칙 — 데이터 형식·검증·반환 형식의 정의 위치

### B.1 ShopGraph 내부 데이터 모양

```python
_customers: dict[str, dict]   # "C01" -> {"id": "C01", "name": str, "gender": "남" | "여", "age": int}
_products:  dict[str, dict]   # "P01" -> {"id": "P01", "name": str, "kind": str, "style": str,
                              #           "price": int, "stock": dict[str, int]}   # 색상 -> 재고
_purchases: dict[str, dict]   # "T001" -> {"id": "T001", "customer_id": str, "product_id": str,
                              #            "color": str, "qty": int, "date": "YYYY-MM-DD"}
_groups:    dict[str, dict]   # "G-F-20" -> {"id": "G-F-20", "gender": "여", "band": "20대"}
_adj:       dict[str, set[str]]              # 노드 ID -> 이웃 ID 집합 (그룹·고객·상품 모두)
_edges:     dict[tuple[str, str], dict]      # (고객 ID, 상품 ID) -> {"colors": set[str], "count": int,
                                             #                       "total_qty": int, "last_date": str}
_next_ids:  dict[str, int]                   # {"C": 7, "P": 6, "T": 14}
```

- 모든 내부 속성은 `_`로 시작한다. **내부 상태 접근 범위**: 운영 모듈(main·view·search·tools)은 쓰지 않는다 / 테스트는 상태 확인을 위한 읽기·깊은 복사만 허용 (`tests/helpers.py`의 `snapshot(g)`이 `_customers`·`_products`·`_purchases`·`_groups`·`_adj`·`_edges`·`_next_ids`를 깊은 복사해 돌려줌) / 내부 상태 직접 수정은 고장 주입 테스트에만 허용. 이를 위해 새 공개 메서드는 만들지 않는다
- **상태 보호 원칙**: 생성자와 등록·수정 메서드는 외부에서 받은 가변 객체를 내부 상태와 공유하지 않는다. 적용 위치는 셋이다: ① 생성자의 고객·상품·구매 딕셔너리(재고 딕셔너리 포함) ② `add_product`의 `stock` ③ `update_product`의 `stock`. 호출자가 넘겨준 딕셔너리를 나중에 고쳐도 내부가 바뀌지 않는다. 나가는 쪽(조회 반환)의 복사는 B.2
- **생성자 계약** (생성자 규칙의 정의 위치)
    1. 세 인자 `customers`, `products`, `purchases`는 각각 **레코드 딕셔너리의 리스트 또는 None**이다 (None = 빈 리스트). 레코드 모양은 위 B.1의 내부 딕셔너리와 같다 (`id` 포함)
    2. 초기 레코드 자체의 ID는 B.1의 형식·범위(C01~C99, P01~P99, T001~T999)를 만족하고 같은 종류 안에서 중복되지 않아야 한다. B.3의 "ID는 존재해야 함"은 생성 이후 메서드 호출에 대한 규칙이라 초기 레코드에는 적용하지 않는다
    3. 초기 레코드의 나머지 필드는 B.3의 값 규칙(이름, 성별, 나이, 종류, 스타일, 가격, 재고, 수량, 구매일 형식·실제 날짜, 구매 색상이 그 상품 색상 목록에 있음)을 만족해야 한다
    4. 구매 기록의 `customer_id`·`product_id`는 **함께 받은 초기 고객·상품 리스트에** 존재해야 한다
    5. 1~4 검증이 모두 끝난 뒤에 내부 데이터를 복사해 보관하고 그래프를 구성한다. 하나라도 어기면 ValueError이고 객체는 만들어지지 않는다
    6. ID 카운터는 종류별로 초기 레코드의 가장 큰 번호 + 1 (없으면 1)
    - 목적: data.py에 손으로 적은 시연 데이터의 실수를 프로그램 시작 시점에 바로 잡기 위해서다. 날짜 검증 함수가 W3에 필요한 이유이기도 하다 (11.3.2)
- 가중치 = `len(_edges[(고객 ID, 상품 ID)]["colors"])`, 간선이 없으면 0
- 최근 구매일은 문자열 최댓값으로 구한다. 저장되는 날짜가 모두 `YYYY-MM-DD` 형식이라 문자열 비교 = 날짜 비교가 성립한다 (B.3 날짜 규칙이 이 전제를 지킨다)
- ID 발급
    - 고객·상품은 두 자리(C01~C99, P01~P99), 구매는 세 자리(T001~T999)
    - 생성자에서 초기 데이터의 가장 큰 번호 + 1로 카운터를 정한다 (초기 데이터가 없으면 1)
    - **모든 검증을 통과한 뒤에만** 번호를 발급한다. 검증에 실패한 등록은 번호를 쓰지 않는다
    - 발급할 때만 카운터가 1 늘어난다. 삭제해도 줄지 않고, `rebuild()`도 카운터를 바꾸지 않는다 → 삭제된 ID는 재사용하지 않는다
    - 한도(C99, P99, T999)를 넘으면 ValueError("ID 한도 초과"). 시연 규모에서는 일어나지 않으므로 테스트 1개로만 확인하고 그 이상 다루지 않는다
- 그룹 ID: `G-{F|M}-{10|20|30|40+}`, 생성 시 8개 전부 만듦
- 상수: 종류 = (상의, 하의, 아우터), 스타일 = (캐주얼, 미니멀, 스트릿, 포멀), 가중치 상한 = 3, K 기본값 3·최대 10

### B.2 반환 형식

**ShopGraph 조회 메서드** — 모두 새로 만든 객체(복사본)를 돌려준다. 돌려받은 값을 고쳐도 내부는 바뀌지 않는다.

| 메서드 | 반환 | 없을 때 |
|---|---|---|
| `get_customer(customer_id)` | B.1 고객 딕셔너리의 복사본 | ValueError |
| `get_product(product_id)` | B.1 상품 딕셔너리의 복사본 (`stock`도 복사) | ValueError |
| `get_purchase(purchase_id)` | B.1 구매 딕셔너리의 복사본 | ValueError |
| `customer_ids()`, `product_ids()` | `[ID]`, ID 순 | 빈 리스트 |
| `find_customers_by_name(name)`, `find_products_by_name(name)` | `[ID]`, 앞뒤 공백 제거 후 완전 일치, ID 순 | 빈 리스트 (공백뿐인 이름은 ValueError) |
| `neighbors(node_id)` | `[이웃 ID]`, ID 순 | ValueError |
| `edge(customer_id, product_id)` | `{"colors": 정렬 리스트, "count", "total_qty", "last_date"}` (새 딕셔너리) | 없는 고객·상품 ID면 ValueError, 둘 다 있는데 간선이 없으면 None |
| `weight(customer_id, product_id)` | int | 없는 고객·상품 ID면 ValueError, 둘 다 있는데 간선이 없으면 0 |
| `group_of(customer_id)` | 그룹 ID | ValueError |
| `members(group_id)` | `[고객 ID]`, ID 순 | 없는 그룹이면 ValueError, 소속 없으면 빈 리스트 |
| `is_sold_out(product_id)` | bool (모든 색상 재고가 0) | ValueError |
| `available_colors(product_id)` | 재고 > 0인 색상 정렬 리스트 | ValueError |
| `stats()` | `{"groups", "customers", "products", "membership_edges", "purchase_edges", "purchases"}` (모두 int) | - |
| `check_integrity()` | `[위반 설명 문자열]`, 정상이면 `[]` | - |
| `delete_customer` / `delete_product` | 함께 삭제된 구매 기록 수 (int) | ValueError |

**search.py** — 가고정(W1), W8b에서 최종 고정

| 함수 | 반환 | 순서 |
|---|---|---|
| `find_products(g, kind=None, style=None, color=None, price_min=None, price_max=None)` | `[상품 ID]` | ID 순 |
| `products_of(g, cid)` S1 | `[{"product_id", "name", "colors": 정렬 리스트, "weight", "count", "total_qty", "last_date"}]` | 상품 ID 순 |
| `customers_of(g, pid)` S2 | `[{"customer_id", "name", "group_id", "colors": 정렬 리스트}]` | 고객 ID 순 |
| `members_of(g, gid)` S3 | `[고객 ID]` | ID 순 |
| `group_popular(g, gid, k=None)` S4 | `[{"product_id", "score", "buyers", "sold_out": bool}]` (품절 상품도 포함하고 표시만) | 점수↓ → 구매자 수↓ → ID↑. k=None이면 전체, 아니면 앞에서 k개 |
| `recommend(g, cid, k=3)` | `[{"product_id", "score", "buyers", "scope": "group" \| "gender" \| "all", "supporters": [고객 ID, ID 순], "available_colors": [색상]}]` | 범위 순(좁은 범위 먼저), 같은 범위 안에서는 점수↓ → 구매자 수↓ → ID↑ |

- `score`는 그 항목의 `scope` 안에서 계산한 값이다. 범위가 다른 항목끼리는 비교하지 않는다 (5.3.3)
- `recommend()` 반환의 `buyers`는 같은 항목의 `len(supporters)`와 같아야 한다 (테스트로 확인). S4(`group_popular`)는 `supporters`를 돌려주지 않으므로 이 규칙의 대상이 아니다
- 결과가 없으면 빈 리스트. "추천할 상품이 없습니다" 같은 문구는 view.py가 출력

**view.py** — 가고정(W1), W8b에서 최종 고정. 모두 print만 하고 None을 반환한다. 테스트는 `contextlib.redirect_stdout`으로 출력 문자열을 확인한다.

### B.3 입력 검증 규칙

| 항목 | 규칙 |
|---|---|
| 정수 공통 | `int`만 인정하고 `bool`(True/False)은 거부. 문자열 "3"도 거부 (문자열 → 정수 변환은 main.py가 담당) |
| 이름 | 앞뒤 공백 제거 후 1~20자 |
| 성별 | "남" 또는 "여" (메뉴에서는 1/2를 고르게 하고 main.py가 변환) |
| 나이 | 정수 10~99 |
| 종류 | 상의 / 하의 / 아우터 |
| 스타일 | 캐주얼 / 미니멀 / 스트릿 / 포멀 |
| 가격 | 정수 0 이상 |
| 색상별 재고 | 색상 1개 이상, 색상명 앞뒤 공백 제거 후 1~10자, 재고 정수 0 이상. 공백 제거 후 같은 색상명이 두 번 나오면(예: "카키"와 " 카키 ") ValueError |
| 재고 수정 | `update_product(stock=...)`은 **통째로 교체**. 새 딕셔너리에 없는 색상은 삭제로 본다 |
| 색상 삭제 | 그 색상의 구매 기록이 없을 때만. 하나라도 있으면 수정 전체를 거절 |
| 구매 색상 | 그 상품의 색상 목록에 있어야 함 (재고 비연동 규칙이라 재고 0이어도 기록은 가능) |
| 구매 수량 | 정수 1~99 |
| 구매일 | ① 정확히 `YYYY-MM-DD` 10자 (정규식 `^\d{4}-\d{2}-\d{2}$`) ② `datetime.date.fromisoformat`으로 실제 날짜인지 확인. **②만 쓰면 안 된다**: Python 3.11부터 `20261023`, `2026-W43-5`도 날짜로 변환돼 통과한다 (직접 실행 확인). 형식이 섞이면 최근 구매일 문자열 비교가 깨진다 |
| 수정 함수 | 바꿀 항목을 하나도 주지 않으면 ValueError("바꿀 항목이 없습니다") |
| 구매 수정 | 색상·수량만 수정 가능. 고객·상품·날짜를 바꾸려면 삭제 후 새로 등록 |
| 조건 조회 | 종류·스타일은 상수 목록 안의 값만, 가격은 정수 0 이상, `price_min > price_max`면 ValueError |
| K | 정수 1~10, 기본 3. `group_popular`의 k는 None(전체) 또는 정수 1~10 |
| ID | 메서드 호출에서 받는 ID는 존재해야 함. 형식이 틀린 ID도 "존재하지 않는 ID" 오류. 생성자의 초기 레코드 ID는 B.1 생성자 계약 2번 |
| 생성자 | B.1 생성자 계약 1~6번 |
| 순서 | 모든 검증을 먼저 하고, 하나라도 실패하면 아무것도 바꾸지 않음 (ID 발급 포함). 유효한 값과 틀린 값을 섞어 줘도 유효한 값까지 반영하지 않음 |

### B.4 경계 상황 체크리스트 (단계마다 해당 항목의 테스트를 둔다)

- 구매 이력이 없는 신규 고객
- 소속 고객이 없는 그룹 / 대상 고객 말고는 동료가 없는 그룹
- 점수 동점 (구매자 수 → ID 순으로 갈리는지)
- 전부 품절인 상품 / 일부 색상만 품절인 상품
- 가중치 4 이상 (상한 3 적용)
- 같은 색 재구매 (가중치 그대로, 기록 수 증가)
- 반복 구매 중 하나 삭제 (간선 유지, 최근 구매일 갱신) / 마지막 기록 삭제 (간선 삭제)
- 구매 수량 수정 (총수량 갱신, 가중치 그대로)
- 고객·상품 삭제 시 연쇄 삭제
- 성별·나이 수정으로 그룹 이동
- 없는 ID, 형식이 틀린 값, 범위 밖 숫자, 빈 문자열, bool, 숫자 문자열
- 날짜 함정: `20261023`, `2026-W43-5`, `2026-02-30`, `2026-1-5`
- 후보가 K보다 적음 / 후보 0개 / 범위가 바뀌는 경우 (범위 표시, 점수 비교 불가)
- 동명이인 조회, 이름 앞뒤 공백, 부분 일치 아님
- 구매 기록이 있는 색상 삭제 시도 (거절) / 색상 추가 (성공)
- 바꿀 항목 없는 수정
- 가격 범위 거꾸로
- 조회 반환값을 고쳐도 내부 불변 (get_customer, get_product, edge)
- 삭제 → rebuild 뒤 ID 재사용 안 함
- 무결성 검사기 고장 주입 4종 (위반 보고 + 다시 불러도 보고 + 검사 전후 상태 동일)
- 같은 성별의 다른 연령대 그룹에만 있는 후보 (같은 성별 범위 합산, 6.3-6번)
- 마지막 구매 기록 삭제 / 상품 삭제 연쇄 / 구매 색상 수정
- 추천 결과 0개 (전 상품 품절)
- 넘겨준 딕셔너리를 나중에 고침 (생성자, add_product, update_product)
- 유효한 값과 틀린 값을 섞은 수정 / 실패한 등록 뒤 다음 ID
- 생성자의 중복 ID·없는 참조 / 공백 제거 후 겹치는 색상명
- 없는 ID로 edge()·weight() 호출 (오류) vs 있는 두 노드 사이 간선 없음 (None·0)

### B.5 6장 ↔ 테스트 대응표 양식 (실제 표는 docs/test_map.md, 테스트 개수가 아니라 이 표로 누락을 확인)

W0에서 이 양식을 `docs/test_map.md`로 복사하고, W2에서 테스트 이름 칸을 채운다 (계획서 본문은 AI가 고치지 않기 위해 분리). 한 테스트가 여러 항목을 맡아도 되고, 한 항목을 여러 테스트로 나눠도 된다. **각 항목은 여기 배정된 단계에서 통과해야 한다** (6.5). 배정 원칙: 그 항목이 부르는 함수 중 가장 늦게 구현되는 함수의 단계.

**W2 게이트에서 확인하는 것** (새 절차가 아니라 W2 기대값 승인의 내용): ① W2 대상 행(화면·흐름 행 제외)의 테스트 이름 칸이 모두 채워짐 ② 승인 담당자가 각 행 테스트의 **확인문(assert)이 그 규칙을 실제로 검사하는지** 읽음. 테스트 이름에 "검증"이 들어 있는 것과 그 검증을 수행하는 것은 다르다 ③ 이 표는 6장 중심이다. B.3·B.4의 규칙 중 표에 행이 없는 것은 G2·G5의 경계 상황 점검에서 테스트를 추가하고, 추가한 테스트 이름을 아래 "기타" 행에 적는다
