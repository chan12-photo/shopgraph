## 측정 조건과 v3 부록 A 정리

- 표준 라이브러리만 사용했다. `main.py` 실행 경로에는 추가하지 않았다. 운영 코드·기존 테스트·금지 파일을 변경하지 않았다.
- 시드 1, 기본 C/P/T=10,000/1,000/300,000. v3와 같은 호출 순서로 성별·10~60세, 상품 색상 2~4개/재고 1~5, 구매 절반의 파레토 쏠림·수량 1~3을 생성한다. 같은 Python 환경에서 같은 시드와 규모이면 같은 데이터다. Python 버전을 넘는 난수 구현의 동일성은 보장하지 않는다.
- **측정 프로세스 안에서만 `graph._ID_PATTERNS`·`graph._ID_DIGITS`를 6/6/7자리로 바꿔 끼웠다. 현재 운영 ID 형식 C99·P99·T999의 한도를 우회한 측정이다. 운영 코드는 바꾸지 않았다. X2에서 검증이 분리되면 이 방식이 바뀔 수 있다(v3 5.5). X1 이후 정식 ID 규칙을 쓰도록 측정 도구를 갱신해야 한다.** 문맥 종료 시 원래 상수 객체를 `finally`로 복구한다. 그 외 운영 객체 내부 속성 접근은 없다.
- time은 추적을 켜지 않는다. 입력 생성·해시·대상 선택·명시적 `gc.collect()`·결과 확인·결과 해제는 시간 구간 밖이다. 호출 도중 자동 GC는 기본값을 유지한다. 생성은 `ShopGraph` 생성자(검증·복사·그래프 구축)를 뜻하며, 데이터 생성·프로세스 시작 시간을 포함하지 않는다. 생성 표본 사이 객체를 해제하고 명시적 수집을 한다. 같은 프로세스의 반복이라 캐시·할당기 재사용 영향이 있다.
- 고객·상품·색상·삭제 대상을 먼저 선택하고, 구매 등록의 반환 ID를 수정·삭제에 쓴다. 첫 구매 5건의 고객/상품/색상을 대상으로 수량 1·2026-10-01을 등록하고 수량 2로 수정한 뒤 단건 조회·추가분 삭제를 한다. 등록 직전 쌍당 기록 수는 3, 1, 8, 11, 1건이다. 대상 쌍은 JSON에 전부 기록했다.
- 일반 변경은 한 그래프에서 순서대로 5건의 미리 정한 작업을 한다. 매 표본마다 원본 상태로 되돌리지는 않으며, 같은 시드·순서로 재실행한다. 쌍당 기록 수와 삭제 영향이 다른 5건의 중앙값이라는 한계가 있다. 조회·추천은 같은 상태를 반복한다. 구매 추가분 삭제 뒤 고객을 등록하고 그룹 이동·재고 수정·고객 삭제를 수행한다.
- 추천 K=3·10은 같은 신규 여성 25세 `C010001`, 그룹 `G-F-20`(대상 포함 1,055명)이다. K=10은 10개 모두 group 범위에서 반환했다. S4는 같은 그룹, k=None으로 전체 순위를 계산한다.
- 고객 삭제는 C000001~C000005. 함께 삭제한 구매는 순서대로 26/36/31/36/29건, 구매 간선은 15/26/20/23/20개다. 삭제 반환값을 미리 집계한 수와 대조했다.
- 재고 변경은 P000001~P000005의 기존 모든 색상에 +1, 그룹 이동은 C000001~C000005의 성별을 반대로 바꾸는 작업이다. 인기 상품 삭제는 **매번 새 원본 그래프**에서 P000001의 구매 84,793건·구매 간선 9,994개를 삭제한다. 이 준비·무결성 확인은 시간 구간 밖이다.
- 전부 품절은 모든 기존 색상 재고를 0으로 만든 **별도 상품 입력**과 같은 구매 입력으로 그래프를 구성하고 같은 신규 고객에게 실제 `recommend(..., 3)`을 호출했다. 내부 재고 직접 변경은 하지 않았다. 세 범위를 탐색하는 스트레스 사례이며 최악 시간은 아니다. 반환값이 빈 리스트인지 시간 구간 밖에서 확인했다.
- 각 변경 묶음 뒤, 품절 그래프·인기 상품 삭제 뒤 `check_integrity() == []`를 시간 구간 밖에서 확인했다. 시간으로 측정한 무결성 검사 결과도 구간 밖에서 전부 `[]`임을 확인했다. 시간 무결성 검사는 변경 뒤 상태(고객 10,001명·상품 1,000개·구매 299,842건·구매 간선 198,649개)다. mem/rss의 무결성 검사는 원본 30만 건이다.
- v3 7.1의 DB 단건 조회는 현재 DB가 없으므로 메모리 `get_purchase`로 따로 측정하고 DB 없음으로 표시했다. SQLite 측정이나 구현은 하지 않았다.

## v3 3장 Linux 컨테이너 수치와의 차이

v3는 Linux x86_64/Python 3.13.17/6cb44e0, 별도 Codex 재측정은 Python 3.12.14다. 이번은 Mac arm64/M5 Pro/Python 3.14.7/a75d130이다. 하드웨어·OS·할당기·인터프리터·기준 코드와 측정 준비 방식이 다르다. 특히 v3 부록 A는 시간 구간 안 대상 조회·선택, 내부 재고 변경을 포함했지만 이번은 구간 밖 대상 선정·별도 품절 입력을 쓴다. 현재 추천 코드는 부족분을 채울 때도 범위를 넓힌다. Linux와의 차이를 운영 코드 최적화 효과나 Mac CPU만의 효과로 해석할 수 없다.

30만 건에서 v3 생성 1,900~2,100ms 대비 이번 598.533ms, 고객 등록 1,280~1,340ms 대비 271.996ms, 구매 등록 1,230~1,250ms 대비 273.177ms, K=3 56~65ms 대비 19.139ms, 품절 추천 790~840ms 대비 259.950ms, 무결성 3,000~3,200ms 대비 857.848ms다. **환경이 달라도 변경마다 전체 재구축하는 비용이 일반 추천보다 크다는 경향**은 이번 측정에서도 보인다. 원인별 기여율은 분리 측정하지 않았다.

추적량은 v3 입력 133MB/보유 270MB/초기화 최댓값 356MB 대비 이번 132.922/271.410/358.002MB로 비슷하다. 일반 실행 최대 RSS는 v3 입력 후 148MiB/그래프 후 372MiB 대비 이번 165.766/396.328MiB다. RSS에는 인터프리터·입력·그래프·임시 할당 등이 들어가고 해제/재사용 방식도 달라 추적량과 동일시할 수 없다. v3의 추적 켠 RSS 664MiB를 일반 RSS 비교에 쓰지 않았다. 이번 무결성 중 추적 최댓값 446.617MB와 검사 후 누적 RSS 489.281MiB는 단계가 달라 v3 초기화 수치와 직접 비교하지 않는다.
